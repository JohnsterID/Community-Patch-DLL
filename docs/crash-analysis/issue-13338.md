# Crash analysis — Issue #13338 "crashes when starting map, 0 civs" (VP 5.4.6)

**Verdict:** REAL POSITIVE, DLL working as designed — the primary signature is
a deliberate ASSERT trap ("Zero possible players?") fired because the map was
generated with zero major civilizations; root cause is the Really Advanced
Setup modmod shipping a stale `MapmakerUtilities.lua` override that shadows
VP's own. A secondary signature in the same user's crashes.log
(`lua51_Win32.dll+0x2f05`) is engine-side and unfixable in our code.

## Primary signature — the attached dump

`CvMiniDump_20260901_120835_5.4.6-0-gb9ddca9a9_Release.dmp`

```
Exception 0xC000001D (Illegal Instruction) in thread 0x7fdfc
Faulting address: CvGameCore_Expansion2.dll+0x58D2E1 = CvAssertDlg+0x331
crashes.log: Location (in file) 0x58c6e1 → +0xC00 (.text raw→VA) = RVA 0x58D2E1 ✓
```

The bytes at that RVA are `0F 0B` (`ud2`) — verified in the 5.4.6 Release DLL
at file offset 0x58c6e1. This is the `BUILTIN_TRAP()` in the `default:` branch
of the MessageBoxA result switch in `CvAssertDlg` (CvGameCoreUtils.cpp:251) —
i.e. the user pressed **Cancel — "Exit the game"** on the assert dialog, and
the 0xC000001D "crash" is that dialog's intentional exit path. (MB_DEFBUTTON2
makes Cancel the default button, so pressing Enter also produces this
signature.)

## The failed check, recovered from dump memory

The assert text is still in the crashed thread's stack memory inside the dump
(recovered via the MINIDUMP_MEMORY_LIST reader at VA 0x10eab8 / raw offset
~800743):

```
Message: Zero possible players? Uhhh...
Expression: iPossibleCount > 0
File: ...\CvGameCoreDLL_Expansion2\CvTeam.cpp
Line: 884
```

That is `CvTeam::DoBarbarianTech()`:

```cpp
// See how many majors are still around
for (iTeamLoop = 0; iTeamLoop < MAX_CIV_TEAMS; iTeamLoop++)
    if (GET_TEAM(eTeam).isAlive() && !GET_TEAM(eTeam).isMinorCiv())
        iPossibleCount++;

ASSERT(iPossibleCount > 0, "Zero possible players? Uhhh...");
```

With 0 civs the subsequent math is guarded (`max(1,...)`), so ASSERT (not
PRECONDITION) is the appropriate severity per project policy. Blame: assert
re-enabled 2025-09-25 (8cf34a0a6); original logic is 2018-era.

## Root cause — RAS MapmakerUtilities override

The game started with zero alive major civilizations, matching the issue
title ("Has 0 civs") and the unresolved civ/leader screen. From the issue
comments plus repo history:

- VP added its own `MapmakerUtilities.lua` in commit df90f3a5e (2026-06-06,
  the big AssignStartingPlots rework, under
  `(1) Community Patch/Core Files/Overrides/Includes/`).
- Really Advanced Setup v15 ships an older `LuaOverrides/MapmakerUtilities.lua`
  that shadows it => `AssignStartingPlots` fails => 0 civs placed.
- A commenter confirmed that deleting RAS's copy fixes it.

Logs corroborate a crash at game setup: Lua.log/net logs sparse (fresh
session); Gamecore.log only benign GreatWorkSlot warnings.

Possible improvement (not implemented): VP could detect a stale
MapmakerUtilities override via a version marker and log a clear error naming
the conflicting mod.

## Secondary signature — lua51_Win32.dll+0x2f05 (fully traced)

The same user's crashes.log contains earlier 5.4.5 entries at
`lua51_Win32.dll+0x2f05`. Traced via IDA (lua51_Win32.dll and
CivilizationV_DX11.exe databases):

- Address reconciliation: crashes.log "in file" +0x2f05 is a RAW FILE offset;
  .text raw 0x400 / VA 0x1000 => RVA = 0x2f05 + 0xC00 = **0x3b05** (matches
  the "live memory" form 0x67a23b05).
- RVA 0x3b05 is inside the exported **`luaL_unref`** (function start 0x3ac0).
  Crash instruction: `mov [ecx], edx` where `ecx = [L+8] = L->top` — the
  standard Lua 5.1 luaL_unref (t[ref]=t[FREELIST_REF]; t[FREELIST_REF]=ref)
  with the stack push inlined.
- An AV writing through `L->top` means `L` was readable but `L->top` was
  garbage/unmapped: a stale or partially-destroyed `lua_State`
  (use-after-free / state reload), or corruption under memory exhaustion.
  NOT a bounds overflow in our DLL.
- Callers (xrefs to the EXE's import thunk 0x923af0): 7 call sites, all
  engine-side Lua-reference RAII wrappers — e.g. `sub_905220` =
  `LuaRef::release { if (m_L && m_ref != LUA_NOREF) luaL_unref(m_L,
  LUA_REGISTRYINDEX, m_ref); }` — firing when engine-held script references
  are released (UI teardown / exit-to-menu / object destruction).
- The 23/08 crashes.log entry shows Sub2G largest free block 3200 KB (~36 MB
  free total) => severe VA exhaustion at that crash. The corresponding dump
  was not attached, so registers are unverifiable, but the instruction-level
  trace pins the failure mode.

Classification: engine-side (Firaxis binaries), distinct from the primary
assert, real crash but not fixable in our codebase; mitigations are reduced
memory pressure and removing broken mod overrides.

## Relationship to the implemented fixes

This issue (together with #13327) motivated the Lua-boundary unit-type
validation implemented on branch `fix-lua-initunit-db-guards` — both issues
demonstrated that modmod scripting errors reaching DLL preconditions kill the
whole game with an opaque Illegal Instruction.

Separately, this user's crashes.log shows `Largest free block (Sub2G): 580 KB`
— severe address-space pressure worth trimming the mod list for, but not what
triggered this particular abort.
