# Crash analysis — Issue #13262 "Game crash" (VP 5.4.2)

**Verdict:** Real crash, NOT a discrete DLL bug — severe **below-2GB (Sub2G)
address-space pressure/fragmentation** in an LAA process that already sits at
~1.7 GB Sub2G committed on load. The `eip=0` execute-AV is a call through a
NULL function pointer / corrupted vtable slot; effectively the same systemic
memory class seen in #13270 and #13344.

**Correction (v2):** an earlier version of this analysis called the dump
flat "32-bit address-space exhaustion". That was imprecise for this dump:
its own crash-time markers show a 10.4 MB largest free Sub2G block and a
1.6 GB contiguous free block above 2 GB, so *total* VA was not exhausted
and a generic heap allocation should not have failed at that instant. The
refined picture below distinguishes what the evidence proves from what it
does not.

## Dump

`CvMiniDump_20260801_171010_5.4.2-0-ga8a136d02_Release.dmp`, analyzed with the
matching official 5.4.2 Release PDB (DLL base 0x6EE20000, size 0x1388000,
RSDS GUID `32A51E99E75AAEAB4C4C44205044422E` — exact PDB match).

```
Exception 0xC0000005 (Access Violation), execute (DEP) of address 0x0
Thread 0x5f08
eax=0x00000000  ebx=0x0214E408  ecx=0x00000000  edx=0x02761090
esi=0x02761080  edi=0x02589000  ebp=0x00000000  esp=0x071FFCCC
eip=0x00000000  eflags=0x00010202
```

`eip = 0` with an execute-AV means control jumped to address 0 — a call
through a NULL function pointer / corrupted vtable slot. There is no faulting
instruction to symbolize.

## The `???+0xfffff400` crashes.log entries decoded

The recurring `???+0xfffff400` lines in this user's crashes.log are this same
signature: the in-game logger subtracts the .text VA-to-file delta (0xC00)
blindly, and `0 - 0xC00` wraps to `0xfffff400`. So those entries are all
`eip=0` crashes. (Logger-side improvement: special-case eip=0; the file-offset
handling was addressed in PR #13347's crash-handler changes.)

## Memory state at the crash — what is and is not proven

crashes.log markers for this dump (17:10:10 01/08):

```
Sub2G: committed 1,681,600k / free 34,736k / largest free block 10,432k
Total: committed 2,044,172k / free 1,737,752k / largest free block 1,681,600k (base 0x968B0000)
```

The dump's own `SystemMemoryInfoStream`/`ProcessVmCountersStream` (parsed
directly) add the system side:

```
Host: 31.8 GB RAM, 20 logical processors
System commit: 21.7 GB used / 34.1 GB limit (17 GB available) — NOT exhausted
Process: WorkingSet 1366 MB, PrivateUsage ~1.6-2.4 GB — consistent with the VA scan
```

So, precisely:

- **Proven:** the Sub2G region is under severe pressure — 1.68 GB of the
  <2 GB space committed, only 34 MB free, fragmented into blocks of at most
  10.4 MB. Across the user's 29 logged crashes the largest Sub2G block
  repeatedly collapses to **428–768 KB**. In *every* entry the big free block
  sits **above 2 GB** (base ≥ 0x80000000).
- **Ruled out:** system commit-limit exhaustion (17 GB available commit at
  crash time) and total-VA exhaustion (1.6 GB contiguous free above 2 GB;
  the process is LAA and demonstrably commits above 2 GB — Total committed
  2,044 MB vs Sub2G 1,683 MB).
- **Not directly proven:** that a specific allocation returned NULL at this
  instant. With 1.6 GB contiguous free above the 2 GB line, a plain
  `malloc`/`new` in an LAA process should succeed. The failure mechanism
  must therefore be **Sub2G-constrained**: allocations made by code that is
  not LAA-aware (legacy allocators, libraries, or anything that masks/asserts
  on the sign bit of a 32-bit pointer), or components that explicitly request
  below-2GB memory. The engine's own crash handler tracks Sub2G separately
  for exactly this reason. Which component makes the failing Sub2G-bound
  allocation is unknown — the failure surfaces far from its cause as a NULL
  fn-ptr call (`eip=0`), Lua state corruption (`lua51_Win32.dll+0x2f05` =
  `luaL_unref` via stale `lua_State::top`, see #13338), or CvGameDatabase AVs.

The one `0xE06D7363` (C++ exception → `bad_alloc` class) entry on 31/07 fired
with 35 MB Sub2G free / 2 GB contiguous Total free, which is consistent with a
Sub2G-bound allocator failing while total VA was plentiful.

## History across the 29 crashes.log entries

- 15+ crashes with the identical `eip=0` signature spanning 5.3.3 → 5.4.2
- plus `lua51_Win32.dll+0x2f05` entries (= `luaL_unref` writing through a
  stale `lua_State::top`; see the #13338 secondary-signature analysis)
- plus several `CvGameDatabase` offsets

A "signature roulette" across modules for one user, with the largest free
Sub2G block ranging 428 KB – 10 MB while a >1 GB block always remains above
2 GB. That pattern — plus the reporter loading a late-game save that puts
Sub2G at ~1.7 GB committed immediately — is why the crash reproduces at load
rather than degrading over hours. A PC restart "sometimes helping" is
consistent with run-to-run variance in module placement/ASLR and system cache
state changing how much Sub2G headroom the process starts with, not with a
per-process fragmentation build-up (that would be cured by restarting the
game alone).

## Conclusion

Real crash; the root cause is Sub2G address-space pressure/fragmentation on a
very late-game save, with the failing allocation made by a component that
needs below-2GB memory. No specific code defect at the crash site. The
mitigation track is memory-reduction/diagnostics work (e.g. #13347's
tactical-plot reserve, MemoryPressure/MemoryAttribution instrumentation), not
a point fix.

Diagnostic gap this issue exposed: crashes.log records VA-scan numbers only.
The dump's `SystemMemoryInfoStream`/`ProcessVmCountersStream` had to be parsed
by hand to rule out commit exhaustion. Adding `GlobalMemoryStatusEx` /
`GetProcessMemoryInfo` fields (available commit, working set, private bytes)
to the crash handler's memory markers would settle VA-vs-commit questions from
the log alone in future reports.
