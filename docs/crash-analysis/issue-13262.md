# Crash analysis — Issue #13262 "Game crash" (VP 5.4.2)

**Verdict:** Real crash in the game executable, not in the VP DLL. The main
thread's per-frame command buffer in `CivilizationV_DX11.exe` overflowed. The
buffer is a fixed 4 MB, and the code that appends to it never checks capacity.
This frame had queued 4.43 MB. The executor ran past the end of the buffer and
called an empty handler slot, which is the `eip=0` execute-AV. No allocation
failed. The low-memory figures are real, but they are not what failed.

**Correction (v3):** v1 and v2 of this analysis listed "call-site-verified stack
frames" in `CvPlayer::setTurnActive` / `doTurnPostDiplomacy` / `DoEvents` /
`doInstantYield` and attributed the crash to AI turn processing, then to
below-2GB address-space pressure. Those frames were artifacts. The analyzer read
each thread's stack descriptor 4 bytes too far into the dump's thread list, so
every thread's "stack" was the same unrelated slice of the dump file. That is
why the same frames appeared in three different threads. The analyzer is fixed
(real x86 unwinding from the PDB's unwind data, branch `clang-linux`, commit
2877e06a2), and the stack below comes from it, with each executable call site
checked by disassembly.

## What failed

`sub_6A5970(buffer, handlers)` walks a buffer of variable-length records:
`[size][type][pad][pad][payload…]`, starting at `buffer+0x80`. It stops when it
reaches `buffer + *buffer + 0x80` (the header holds the used size), and for each
record calls `handlers[type].fn(payload, handlers[type].ctx)`. The disassembly
fixes the register roles: `esi` = current record, `edi` = end, `ebx` = handler
table.

- **The buffer is static.** The command queue is a global object inside the
  EXE (IDA 0x1A0E400, at runtime 0xB40000 + 0x160E400 = `0x214E400`). It holds
  a double-buffered pair of 4 MB buffers (stride 0x400080: a 0x80 header plus
  0x400000 of data) and a table of about 190 handler slots. Static initializers
  register the handlers at startup.
- **Writers do not check capacity.** Every writer reserves space with
  `InterlockedExchangeAdd(&header->size, recordSize)` and writes at
  `header + 0x80 + oldSize`. There is no capacity check. Example:
  `sub_610940` (type 114, 256 bytes).
- **This frame overflowed the buffer.** The executor's arguments are still on
  the stack at the crash: `[esp+0x1C]` = buffer `0x214F080` (the first half),
  `[esp+0x20]` = handler table `0x214E408` (= `ebx`). The end pointer is
  `edi = 0x2589000`. So the used size was `0x2589000 − 0x214F080 − 0x80 =
  0x439F00`, which is **4,431,616 bytes against a 4,194,304-byte capacity**.
  The writers had run 237 KB past the end of the buffer.
- **The executor then walked off the end.** It followed record sizes through
  the overflow and past `edi` (`esi` is 1.9 MB beyond it), executing leftover
  records from earlier frames until it reached a type whose handler slot is
  empty (`eax = ecx = 0`). It then called address 0.

Judging by the record types (draw parameters, bounding boxes initialised to
±FLT_MAX), this is the renderer's command queue. That is an inference from the
writers, not from symbols.

## Cross-check: the same bug in a full-memory dump

A 5.4.2 Debug session of mine (DX9 EXE, build 0x546ccb59) crashed with the same
stack, `sub_420F40` ← `sub_6022D0` ← `sub_484620` ← message loop ← `WinMain`.
The call sites are instruction-for-instruction the same as #1–#3 above, and that
crash also came right after loading a late-game save. Its full-memory dump
contains the buffer itself:

- The header claims `0x764d00` bytes (**7.76 MB**) of commands in one frame:
  26,169 records.
- After the first buffer's 4 MB, the executor reads the second buffer's header
  as a record ("type 15, size 1,906,816") and jumps through it.
- It then reaches an all-zero record. Type 0 is one of 23 unregistered slots,
  so it calls NULL.

## Memory state (real, but not the cause)

crashes.log for this dump:

```
Sub2G: committed 1,682,680k / reserved 379,672k / free 34,736k, largest free block 10,432k
Total: committed 2,044,172k / free 1,737,752k, largest free block 1,681,600k at 0x968B0000
```

The dump's system and process streams show 32.5 GB RAM and 12.7 GB of system
commit still available. Process commit was 1,644 MB, VirtualSize 2,400 MB. The
command buffer is static memory inside the EXE image, so no allocation was
involved in this crash.

## History in this user's crashes.log (29 entries, 5.3.3 → 5.4.2)

- 16 × `???+0xfffff400`: the `eip=0` signature (the old handler subtracted
  0xC00 from 0 and wrapped). crashes.log alone cannot show whether every one of
  these is the same overflow. A dump of each would.
- 1 × `???+0xfffff404` and 1 × `???+0xfffff441`: calls to 0x4 and 0x41. That
  fits the same executor reaching a garbage handler slot, but is unconfirmed.
- 7 × `CvGameDatabaseWin32Final Release.dll` (+0x5c0c ×5, +0x496ea ×2),
  3 × `lua51_Win32.dll+0x2f05` (`luaL_unref` through a stale `lua_State`, see
  #13338), and 1 × C++ exception in KERNELBASE: different signatures, not
  analysed here.

The reporter sees it when loading a save, and a PC restart "sometimes helps".
Both fit a frame that queues more than 4 MB of commands while a big late-game
save is being loaded and its visuals created.

## Conclusion

This is a fixed-size, unchecked command buffer in the game executable. It
overflows when one frame produces more than 4 MB of commands. It cannot be fixed
in the DLL. The only lever on the VP side would be the number of objects and
visual updates issued per frame during load, which needs measuring before
proposing anything.
