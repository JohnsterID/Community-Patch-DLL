# Crash analysis — Issue #13319 "5.4.4 Game Crash" (save load)

**Verdict:** FALSE POSITIVE for the VP DLL — an engine-thrown C++ exception on
a save-stream read failure, local to the reporter's machine. The maintainer
loaded the same save with identical mods successfully; the reporter's machine
also fails on older saves and after full reinstall + verify + C++ redist
repair. Nothing actionable in our codebase.

## Dump

`CvMiniDump_20260824_230014_...5.4.4...ga42699246.dmp`

```
Exception 0xE06D7363 (MSVC C++ exception) raised at KERNELBASE!RaiseException
ExceptionInformation: magic 0x19930520, object 0xaed640, ThrowInfo 0x136b470
```

The ThrowInfo pointer lands in the game EXE (base 0xbe0000 → RVA 0x78b470).

## Decoding the thrown type (ThrowInfo → RTTI)

Walking ThrowInfo → CatchableTypeArray → TypeDescriptor in the EXE image on
disk resolves the thrown type to:

```
.?AVexception@stdext@@   (stdext::exception)
```

Reading the exception object itself from the dump (via MINIDUMP_MEMORY_LIST
ranges — the thread-stack-only reader silently returned wrong bytes for this
object until switching to full memory-list VA reads; this drove one of the
analyze_minidump.py improvements): vtable 0x1362380 (EXE RVA 0x782380),
message pointer 0x11ca4e8 → EXE .rdata string `"unknown"` — i.e. a
default-constructed `stdext::exception`.

## Locating the thrower (IDA, CivilizationV_DX11.exe)

- The only code xref to that ThrowInfo is `sub_82B4C0` (a throw helper).
- Its sole caller is `sub_8377E0`: calls `GetFileSystemMgr()`, invokes
  vtable+56 (a read/open), and THROWS when it returns 0.
- `sub_8377E0` sits in vtable `off_B89800` adjacent to `FIXmlSerialize` /
  `FTimedTrigger` strings = an engine serialization stream class.

So the throw fires when the engine's file-system stream cannot deliver the
requested bytes during save load — designed behavior surfacing a corrupt or
unreadable local stream; unhandled, it becomes the crash dialog.

## Supporting evidence

- Game-DLL pointers on the crashed stack are sparse (9) and symbolize to
  unrelated stale frames (Lua GetSquadMovementPreview, canSeePlot) —
  consistent with the throw originating in EXE stream code, not our DLL.
- crashes.log: both entries `0xE06D7363 KERNELBASE+0x1696b4` within the same
  minute, no prior signature variety (unlike the OOM-class machines).
- Memory is NOT the cause here: committed only ~1.6–1.8 GB, largest free
  Sub2G block 4.5–8 MB — unremarkable.

## Conclusion

Real crash on the reporter's machine; cause = local save-file/stream read
failure (disk/AV/permissions/profile). No DLL action possible or needed — the
throwing code is in the engine executable.

Tooling fallout (implemented on the fork's clang-linux branch):
analyze_minidump.py now decodes 0xE06D7363 params (magic/object/ThrowInfo),
resolves the thrown RTTI type name from the module on disk, and reads what()
strings via MINIDUMP_MEMORY_LIST arbitrary-VA lookups.
