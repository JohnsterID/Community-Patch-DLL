# Crash analysis — Issue #13344 "likely out of memory" (VP 5.4.6, WINE/Proton)

**Verdict:** Real crash, NOT a discrete DLL bug — definitive 32-bit virtual
address space exhaustion (the reporter's own suspicion was correct).
Duplicate-class of #13262/#13270. Two distinct signatures in the report, both
engine/CRT-side manifestations of the same root cause.

## Signature A — the attached dump (5.4.6, 02/09, WINE/Proton)

`CvMiniDump_20260902_224318_5.4.6-0-gb9ddca9a9_Release.dmp`

```
Exception 0xC0000005 (Access Violation), WRITE of address 0x0
Faulting address: msvcrt.dll+0xA38D (WINE builtin msvcrt, base 0x7B7A0000
                  — matches crashes.log msvcrt.dll+0x978d file-offset form)
Registers: eax=0x2000  ecx=0x2000  edx=0x0  edi=0x0  esi=0x096A1000
```

A `memcpy`-type operation inside WINE's C runtime copying 0x2000 (8 KB) bytes
to a **NULL destination**: an allocation upstream returned NULL because the
32-bit process had no contiguous address space, and the result was used
unchecked (engine/CRT side, not the VP DLL).

WINE/Proton confirmed by the module list: wined3d.dll, winex11.drv,
winevulkan.dll, winegstreamer.dll, lsteamclient.dll (91 modules; game exe is
CivilizationV.exe, DX9, for this dump).

Memory markers at this crash (crashes.log): **Total free 65,372 KB, largest
free block (Sub2G) 3,136 KB**, committed ~2.5 GB — textbook exhaustion/
fragmentation.

## Signature B — the recurring `CivilizationV_DX11.exe+0x227ad6` (13 entries, 5.4.2, 12/08)

Every occurrence has largest free block 3072–4096 KB. Same disease, different
symptom. Fully traced:

**RVA mapping** (verified in the DX11 exe database): crashes.log
"Location (in file)" 0x227ad6 is a file offset; .text raw=0x400 va=0x1000
→ RVA 0x2286D6 → IDA VA 0x6286D6 → function `sub_6286D0` (size 0x5D).

**Faulting instruction:** `mov eax, [edx+24h]` — bytes at file offset
0x227ad0: `56 8b 71 4c 8b 16 8b 42 24` = `push esi; mov esi,[ecx+4Ch];
mov edx,[esi]; mov eax,[edx+24h]`. Decompiled: reads `v3 = *(this+76)`, then
`*(*v3+36) - *(*v3+32)` (a begin/end vector pair, 64-byte elements), then
walks 64-byte records flipping a WORD state to 2 when a float time window
matches. The crash is `*v3` (the vector object pointer) being NULL/garbage
while `this+76` itself was readable.

**Subsystem identification** (via the symbol-bearing Linux port build,
Civ5XP): the callers are `sub_6E7180` (per-element anim-state walker: 12-byte
float triples, `1LL << i` bitmask) and `sub_722B20` (iterates 896-byte records
via freelist with 0xFFFFFFF sentinel); grandparent `sub_4B4B80` walks 836-byte
records with `*(int*)(base+836*i+4) < 0` handle-validity checks. In Civ5XP,
exactly ONE function contains both immediates 836 and 896:
`cvUnitSimSystem::OnUnitActionChanged(...UnitActionData...)` — 836-stride =
cvUnitSim records, 896-stride = cvUnitVis records, with the identical
validity-bit pattern and `cvUnitVisSystem::HasAnimation` calls.
`cvUnitSimSystem::UpdateSim(cvUnitSim&, float)` uses the same 896 stride and
freelist sentinel helpers.

**Conclusion for B:** engine-side unit visualization/animation state update
(a cvUnitVis record) dereferencing a corrupt/NULL animation-array pointer.
Under exhaustion, a cvUnitVis or its internal vector fails to allocate → every
affected unit render tick crashes at the identical address — hence 13
identical entries in two hours. Entirely inside the game executable; not
fixable from the VP DLL. Notably, the crash sits in the unit-visualizer path,
which scales with live units on screen — consistent with the confirmed OOM
driver (late-game unit count).

## Overall history

All 18 crashes.log entries for this machine (13x exe+0x227ad6, 3x
ntdll+0x507b9, 1x msvcrt, 1x CivilizationV.exe+0xee1e6) are one root cause:
VA exhaustion driven by a very large mod list (30+ mods incl. 4UC, Squads,
many civs) on Giant maps plus late-game unit/city counts. Sub-2G committed
~1.7 GB with the largest free block shrinking from ~200 MB (early entries) to
3 MB (crash sessions). Game-DLL presence on the crashed stack is stale noise
only (vector dtor / CvWeightedVector fragments; no verified call chain).

The dump also shows >1 GB total reserved (WINE/graphics mappings), matching
the #13270 WINE pattern.

## Practical mitigations for the reporter

1. Cull the biggest asset-heavy mods first (unit/graphics packs, map packs) —
   civ/leader additions load whole asset sets per civ in game.
2. On WINE: ensure the runner respects the large-address-aware flag
   (4 GB VA for the 32-bit process).
3. Building a modpack (Modpack Maker) reduces duplicate loads vs. many
   individually enabled mods.
