# Crash analysis — Issue #13313 "crashes when setting up game" (VP 5.4.5)

**Verdict:** REAL POSITIVE — a DLL-side defect exposed by a corrupted local
install: unchecked `PrepareResults()` NULL return dereferenced in the info-
class DB load path. Root trigger is external (corrupt gameplay database —
Steam "verify game files" fixes it), but the failure mode was an unexplained
NULL-deref instead of a diagnostic.

**Fix implemented:** branch `fix-lua-initunit-db-guards` (commit 4abd43498)
makes `CvDatabaseUtility::PrepareResults` raise a PRECONDITION naming the
failed cache key, the SQL statement, and the SQLite error message.

## Dump

`CvMiniDump_20260823_112942_5.4.5-0-g4803a24c6_Release.dmp`

```
Exception 0xC0000005 (Access Violation), READ of address 0x8
eip = CvGameDatabaseWin32Final Release.dll+0x6844
ecx = 0x00000000
```

crashes.log records the same site as file offset +0x5c44; .text raw 0x400 /
VA 0x1000 gives +0xC00, so file 0x5c44 → RVA 0x6844 — consistent.

## Faulting instruction (IDA, DB DLL)

RVA 0x6844 = VA 0x10006844 is `mov eax, [ecx+8]` inside the exported
`?Bind@Results@Database@@QAE_NHPBD_N@Z` =
`Database::Results::Bind(int idx, const char* szValue, bool bMakeCopy)`,
in the `bMakeCopy=true` path.

`ecx` is `this`. With `ecx = 0`, reading `this+8` (the `m_pStmt` slot) faults
at address 0x8 — matching the faulting address exactly. **This is a NULL
`this` call, not sqlite-level corruption at the crash site.**

## Caller-side defect (our DLL)

The pervasive pattern in CvInfos.cpp and the other info-class loaders:

```cpp
pResults = kUtility.GetResults(key);
if (!pResults)
    pResults = kUtility.PrepareResults(key, "select ...");
pResults->Bind(1, szType);   // <-- no NULL check
```

`CvDatabaseUtility::PrepareResults` returns NULL when the sqlite prepare
fails (`DB.Execute(*pResults, szStmt)` false). Roughly 200 direct call sites
across CvInfos.cpp, CvTraitClasses.cpp, CvBuildingClasses.cpp, etc.
dereference the result unchecked (34+ `Bind(1, ...)` sites in CvInfos.cpp
alone). The internal populate helpers (PopulateArrayBy*, etc.) do null-check —
only the direct call sites don't.

The return-address slot at esp+0xc is zeroed in the dump (stack page partially
zero), so the exact CvInfos caller is unidentifiable, but the register +
instruction evidence is conclusive regardless. git blame: the pattern is
Firaxis-era (2013 import), not a regression.

## Runtime and community evidence

- Crash occurs during "Configuring game data" (game-setup DB caching);
  stopwatch.log shows `SetActiveDLCandMods` completing, then
  `LoadUnitLibraries`.
- Database.log shows benign duplicate-key noise; the
  `no such table: ContentPackage.LocalizedText` noise shows the localization
  attach state was already unusual.
- Commenter fixed the identical symptom via Steam "verify game files";
  the reporter later reinstalled. => corrupted core DB/assets cause a prepare
  failure => NULL return => delayed crash.
- 7 crashes.log entries, all the same signature.

## Why a hard diagnostic (not a soft skip) is the right fix

These Bind calls populate info caches at mod activation; a failed prepare
means the DB schema is broken and the game cannot proceed meaningfully.
Intended behavior on failure is a clear error naming the failed statement —
not an AV several frames later. The implemented fix places the PRECONDITION at
the single failure source inside `PrepareResults` (covers every call site
without touching ~200 callers):

```
Failed to prepare database query '<key>' [<sql>]: <sqlite error>
-- the game database is corrupted or a mod is broken; try verifying game files
```
