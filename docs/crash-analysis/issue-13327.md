# Crash analysis — Issue #13327 "Game crash" (VP 5.4.3)

**Verdict:** REAL POSITIVE, DLL working as designed — a deliberate
PRECONDITION trap in `CvPlayer::initUnit` fired on an invalid unit type
(`NO_UNIT`, -1) passed in from a third-party modmod's Lua bug (Sukritact's
Suzerainty; confirmed by the maintainer in-thread). Same class as #13338's
primary signature; together they motivated the Lua-boundary validation fix.

**Fix implemented:** branch `fix-lua-initunit-db-guards` (commit 4abd43498)
validates the unit type ID at the Lua boundary in `lInitUnit`,
`lInitUnitWithNameOffset` and `lInitNamedUnit` — an invalid ID now raises a
Lua error (traceback in Lua.log, game keeps running) instead of trapping the
whole game.

## Dumps

Two dumps, `CvMiniDump_20260826_040526` and `CvMiniDump_20260828_001028`
(5.4.3, gb83e6cf1e; DLL bases 0x82AC0000 / 0x79D90000):

```
Exception 0xC000001D (Illegal Instruction), thread 0x21e8 (first dump)
Faulting address: CvGameCore_Expansion2.dll+0x9049CD  (BOTH dumps, same RVA)
ebx = 0xFFFFFFFF  (BOTH dumps)
```

crashes.log cross-check: file offset 0x903dcd + 0xC00 (.text raw→VA delta)
= RVA 0x9049CD — consistent.

## Symbolization and trap verification

- llvm-symbolizer with the official 5.4.3 PDB (GUID 0A7CEFCC...):
  RVA 0x9049CD = `CvPlayer::initUnit`, **CvPlayer.cpp:9192** =

  ```cpp
  PRECONDITION(eUnit > NO_UNIT && eUnit < GC.getNumUnitInfos(),
               "Unit is not assigned a valid value");
  ```

- DLL bytes at the RVA: `e8 06 82 c8 ff 83 c4 08 0f 0b` =
  `call` (precondition-report fn); `add esp,8`; `ud2` — the `BUILTIN_TRAP()`
  of a failed PRECONDITION. 0xC000001D is the ud2 instruction.
- Registers: `ebx = 0xFFFFFFFF = -1 = NO_UNIT` — the invalid `eUnit` value
  itself, consistent in both dumps.
- git blame: the PRECONDITION is intentional hardening (re-enabled asserts and
  preconditions, 2025-09-25, commit 8cf34a0a6).

## Root cause (external modmod)

Confirmed by the maintainer in-thread: Sukritact's Suzerainty modmod,
`Lua/Suzerainty_Functions.lua:311` (SUZERAINTRAIT_MINOR_CIV_SUK_URBINO):

```lua
pAlly:GetSpecificUnitType(GameInfoTypes[sClass])
```

The binding expects a STRING class name; `lua_tostring` of the integer yields
e.g. `"82"`; `GC.getInfoTypeForString("82")` = -1 = NO_UNITCLASS =>
`GetSpecificUnitType` returns NO_UNIT (-1) => the mod calls
`pPlayer:InitUnit(-1, ...)` => `lInitUnit` passed it straight to
`CvPlayer::initUnit` => PRECONDITION fires => ud2.

## Why the DLL behavior was "as designed" — and what we changed anyway

`initUnit` must never spawn an invalid unit type (it would corrupt
FFreeListTrashArray indexing and desync multiplayer), so trapping early is the
correct core policy. But the project policy also says to null-check when
interacting with dynamic systems (scripting) — and `lInitUnit` is a Lua-facing
entry point where a modmod bug killed the whole game with an opaque Illegal
Instruction. Hence the boundary validation fix: reject the invalid ID with a
descriptive Lua error naming the bad value and the likely cause (a GameInfo
lookup that returned nil), before it can reach the PRECONDITION.

## Side note on the OOM heuristic

The analyzer flagged "largest free 516 KB — likely OOM" for these dumps. That
is misleading here: the trap is a deterministic PRECONDITION, not an
allocation failure. (Sub2G committed 1,714,016k is high, but the crash cause
is the trap.) The OOM heuristic should remain advisory-only.
