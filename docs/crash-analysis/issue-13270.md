# Crash analysis — Issue #13270 "Crash, 43 civ Giant Earth" (VP 5.4.2, WINE)

**Verdict:** Real crash, NOT a discrete DLL bug — same systemic 32-bit
address-space exhaustion class as #13262/#13344. No minidump exists because
`MiniDumpWriteDump` itself needs memory and the write fails at exhaustion
("crashdumps are completely empty"), exactly as the maintainer suggested
(largest free block 1024 KB in the crash popup).

## Setup and runtime evidence

- 43-civ Giant Earth map (near the engine's practical ceiling), VP+EUI,
  WINE/Proton — same environment class as #13344.
- `net_message_debug.log` ends mid AI auto-moves (player 31 Napoleon,
  `CheckPlayerTurnDeactivate`) = crash during AI turn processing, matching the
  §12.5 late-game AI-turn OOM profile.
- The Lua runtime errors in the logs (VPUI_loader load failure, EUI TopPanel
  `os` nil) are cosmetic/pre-existing, not crash-proximate.

## The `operator new` question — binary-level answer

The thread asked whether the DLL really uses an overridden `operator new` that
returns NULL instead of throwing. Verified at the binary level: **yes**, and
it is not our code.

**Where it comes from.** The prebuilt Firaxis SDK static library
`FirePlace/lib/FireWorksWin32.lib` defines the mangled global symbols
`??2@YAPAXI@Z` (operator new), `??_U@YAPAXI@Z` (operator new[]) and
`??3`/`??_V` (deletes) in the same COFF member (@0x4f0056 in the archive
symbol index) that defines `FireMalloc`/`FireFree`. Our own sources never
define these — the `FXS_MEMORY_MANAGER`/`FXS_MEMORY_TRACKER` defines in
FMemHooks.h are off in our build (VoxPopuli.vcxproj defines neither) — but at
link time every `new` in every translation unit resolves to the FireWorks
definition.

**What it does** (disassembly of the 5.4.6 Release DLL at RVA 0xd43b50, which
the official PDB maps to both `??2@YAPAXI@Z` and `?FireMalloc@...` — identical
bodies, COMDAT-folded):

1. On first call, binds the game EXE's exported small-block allocator via
   `GetProcAddress(GetModuleHandle(NULL), ...)`: `GetSmallObjectAllocator`,
   `FSBAAllocate`, `FSBADeallocate`, etc. All 10 FSBA symbols are exports of
   CivilizationV.exe / CivilizationV_DX11.exe — the DLL and EXE share one
   allocator. (FSBA fptrs at 0x10f44294/98, filled by the `FSBABind` helper at
   0xd43c10.)
2. Tries `FSBAAllocate(size)`.
3. Falls back to plain `MSVCR90!malloc(size)` (IAT 0x10e4a5a0).
4. **Returns whatever that returns — NULL on failure. It never calls
   `_callnewh`, never throws `std::bad_alloc`.**

4,423 direct call sites in the release DLL bind to this stub (measured by
scanning .text relocations to RVA 0xd43b50). Under exhaustion any
`new CvUnit`, any `std::vector` growth, etc. can yield NULL, and the crash
surfaces later at whatever touches the "object" — exactly the signature
roulette across the OOM issues (#13262 eip=0, #13344 NULL-dest memcpy, this
issue's empty dumps). The vanilla Firaxis CvGameCore_Expansion2.dll has the
identical pattern — inherited SDK behavior, not a VP change.

**Why we can't trivially replace it.** The lib member that defines
`operator new` also defines `FireMalloc`/`FireFree`, which other FireWorks
members (FString, FFastVector internals) reference — so that member is always
pulled into the link, and supplying our own `??2@YAPAXI@Z` collides (LNK2005).
There is also a pairing constraint: FSBA-allocated blocks must be freed by
`FSBADeallocate` (via the FireWorks delete), so any replacement must keep the
FSBA path consistently for both new AND delete.

**What a throwing wrapper would buy.** It is technically possible (own
new/delete pair ahead of the lib in link order, FSBA-then-malloc, throw
`bad_alloc` on NULL) but would NOT save the game: the engine EXE has the same
unchecked-NULL behavior internally (see #13344), and an uncaught `bad_alloc`
still terminates. The gain is purely diagnostic — failing at the exhausted
allocation instead of a delayed corrupt-pointer crash. The cheaper equivalent
already exists: the crash handler's "Largest free block (Sub2G)" markers
reliably identify OOM even when eip is garbage.

## WINE-specific observations

Both this issue and #13344 show >1 GB "Total reserved" (vs ~400 MB typical on
Windows) — reservation pressure at the engine/driver level under Proton
(graphics mappings). LAA is enabled in these dumps (maxMemory 4,194,176k =
full 4 GB), so it is not a missing-LAA problem.

## Conclusion

Systemic OOM, duplicate-class of #13262/#13344. No discrete DLL defect.
Actionable follow-ups are diagnostic: flag "dump write failed (likely OOM)"
explicitly in crashes.log, and continue the memory-reduction track (late-game
live-unit quantity is the confirmed driver; corr(LiveUnits, AvailVirtualMB) =
-0.953 in field data).
